# Avito Bootcamp NLP: кандидатогенерация для поиска услуг

По поисковому запросу («автоподбор», «баня на дровах», «обзвон по базе»…) нужно отобрать из корпуса в 189 тыс. объявлений до 50 кандидатов так, чтобы в них попали объявления, которые пользователь в итоге выбрал. Метрика — Recall@50.

**Результат: Recall@50 = 0.899** на бенчмарке. Бейзлайн BM25 + локация давал 0.809.

| Отправка | Что добавлено | val v2 | бенчмарк |
|---|---|---|---|
| sub1 | BM25 (леммы) + локационный приор | 0.817 | 0.809 |
| sub2 | + эмбеддинги e5-small, LightGBM-ранкер над объединёнными кандидатами | 0.883 | 0.867 |
| sub3 | + e5-base, дообученная на кликах из train | 0.898 | 0.881 |
| sub4 | + гео-признаки, кандидаты без сильного приора локации | 0.913 | 0.894 |
| **sub5** | + профиль кликов похожих запросов, косинус e5-small | **0.919** | **0.899** |

«val v2» — наша офлайн-валидация (раздел [Валидация](#валидация)). Её разрыв с бенчмарком стабилен на всех отправках, поэтому решения принимались по ней.

Подробный разбор с графиками — в [`solution.ipynb`](solution.ipynb).

## Быстрый старт

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt          # для GPU: сначала torch с CUDA, см. комментарий в файле
```

1. **Данные.** Три parquet-файла в папке `NLP_avito_interns-dataset/`.
2. **Дообученные модели.** Нужны `models/multilingual-e5-base-ft-val` и `models/multilingual-e5-base-ft-full`. Их можно обучить (на GPU):
   ```bash
   python finetune.py --mode val  --model intfloat/multilingual-e5-base
   python finetune.py --mode full --model intfloat/multilingual-e5-base
   ```
   Либо скачать готовые веса, с которыми получены отправки, с [HuggingFace](https://huggingface.co/serzhik666/multilingual_e5/tree/main), и распаковать в `models/`:
   ```bash
   mkdir -p models && cd models
   curl -LO https://huggingface.co/serzhik666/multilingual_e5/resolve/main/multilingual-e5-base-ft-val.zip
   curl -LO https://huggingface.co/serzhik666/multilingual_e5/resolve/main/multilingual-e5-base-ft-full.zip
   unzip multilingual-e5-base-ft-val.zip && unzip multilingual-e5-base-ft-full.zip && cd ..
   ```
   Обучение на GPU не детерминировано до бита, поэтому побитово совпадающий `answer.csv` получается только с этими весами.
3. **Ответ:**
   ```bash
   python predict.py                       # = --preset sub5, пишет answer.csv
   python check_answer.py answer.csv       # проверка формата по требованиям ТЗ
   ```
   Любую прошлую отправку можно воспроизвести так: `python predict.py --preset sub3 --out answer_sub3.csv`. Все пять пресетов проверены: они побитово совпадают с отправленными файлами (md5 в `solution.ipynb`).

**Время и ресурсы.** Первый запуск с нуля идёт несколько часов на ноутбуке (Apple M3 Pro, 18 ГБ). Большую часть занимают лемматизация корпуса и эмбеддинги ~0.9 млн объявлений. Всё промежуточное кэшируется в `cache/`, повторный запуск занимает минуты. Пик памяти ~9 ГБ. Внешних API нет: модели скачиваются с HuggingFace один раз и дальше работают локально.

## Подход

```
запрос ──┬─ BM25 по леммам (заголовок×3 + параметры + описание) ─────┐
         ├─ bi-encoder: multilingual-e5-base, дообученный на кликах ──┼── + w·log P(локация объявления | локация поиска)
         └─ линейный фьюжн: 0.5·BM25norm + cos + 0.1·log P(loc) ──────┘
                │
    кандидаты = top-300 каждого источника ∪ top-100 фьюжна с малым весом локации   (~570 на запрос)
                │
    LightGBM lambdarank: 29 признаков (текст, локация и гео, подкатегории, профиль кликов)
                │
             top-50
```

Recall@50 не зависит от порядка внутри top-50, поэтому всегда отдаются ровно 50 объявлений: пустые слоты ничего не экономят.

### Данные и признаки: что использовано и почему

| Данные / признак | Почему |
|---|---|
| **Текст объявления** (заголовок, описание, параметры) — BM25 по леммам | Запросы короткие и терминологичные («нитрид титана»), точное совпадение слов — сильный сигнал. Лемматизация pymorphy3 дала +0.07 к «сырому» тексту: «баня на дровах» ↔ «дровяная баня». Заголовок взвешен ×3 (+0.02). |
| **Эмбеддинги** запроса и объявления (заголовок + начало описания) | Синонимы и перефразировки: у 19% запросов бенчмарка нет ни одного объявления со всеми словами запроса. |
| **Локация**: приор P(item_loc \| search_loc) по train | Главный сигнал. При поиске по городу в 93% случаев выбирают объявление из этого же города. Для региональных id (Московская обл., вся РФ) в корпусе нет объявлений с таким id, а приор выучивает «дочерние» города. Мягкий приор лучше жёсткого фильтра (0.870 против 0.813). |
| **Гео**: расстояние до «центра» локации поиска, нормированное на её радиус; ранг локации в регионе | По приору нельзя отличить городок внутри Московской области от города на другом конце страны, а по расстоянию можно. Центр и радиус посчитаны по координатам кликов в train. |
| **Подкатегория** `item_microcat_id`: P(microcat \| текст запроса), P(microcat \| леммы), по соседним запросам, доля в top-50 фьюжна | Категория бесполезна (почти всё — 114 «услуги»), а подкатегория (752 значения) отделяет «ремонт двигателя» от «тюнинга». |
| **Профиль кликов**: косинус кандидата со средним эмбеддингом объявлений, выбранных по 30 самым похожим запросам из train | Коллаборативный сигнал «что люди выбирают по такой потребности». Особенно помог в мегаполисах, где много похожих объявлений. |
| Не использовано: `search_category`, флаги доставки, цена/рейтинг/отзывы, история кликов объявления | Категория и доставка почти константны. Остальное опасно при переносе val → бенчмарк, см. [ловушки](#ловушки-переноса-val--бенчмарк). |

### Модели и алгоритмы

| Компонент | Реализация |
|---|---|
| Лексический поиск | Свой разреженный BM25 на scipy ([src/bm25.py](src/bm25.py)). Готовые библиотеки отдают только top-k, а нам нужны полные векторы скоров для фьюжна. |
| Нормализация | `pymorphy3` (лемматизация), ё→е. Для сравнения пробовал `PyStemmer` (Snowball). |
| Bi-encoder | `intfloat/multilingual-e5-base`, контрастивно дообученный на парах «запрос → выбранное объявление» из train ([finetune.py](finetune.py)): CachedMultipleNegativesRankingLoss, батч 256, 1 эпоха. Не больше 20 пар на текст запроса, иначе «массаж» (6.5 тыс. строк) забивает выборку. Одинаковые запросы не попадают в один батч. Две версии: `ft-val` — на train-fit, для признаков val; `ft-full` — на всём train, для бенчмарка. |
| Второй bi-encoder | `intfloat/multilingual-e5-small` без дообучения, только как признак. |
| Ранкер | `LightGBM` LGBMRanker (lambdarank), обучается на 3000 val-запросах и применяется к бенчмарку ([src/ranker.py](src/ranker.py), [predict.py](predict.py)). |
| Проверен и отвергнут | Cross-encoder `DiTy/cross-encoder-russian-msmarco` (RuBERT-base), дообученный на кликах с hard negatives ([train_cross_encoder.py](train_cross_encoder.py)). Прироста нет, см. ниже. |

Open-source: pandas, pyarrow, numpy, scipy, scikit-learn, pymorphy3, PyStemmer, LightGBM, PyTorch, transformers, sentence-transformers; модели intfloat/multilingual-e5-{small,base} и DiTy/cross-encoder-russian-msmarco с HuggingFace.

## Валидация

Все решения принимались по офлайн-валидации, повторяющей устройство бенчмарка ([src/validation.py](src/validation.py)).

1. **Единица** — группа строк train с одинаковыми (запрос, локация, фильтры, категория). Её выбранные объявления — релевантные. В среднем ~1.1 на запрос, как в ТЗ.
2. **Выборка.** 3000 групп, по одной на уникальный текст (бенчмарк тоже состоит из уникальных текстов). 37% текстов «виденные»: другие группы с этим текстом остались в train-fit, как у 37% запросов бенчмарка. Остальные тексты удалены из train целиком.
3. **Никакой утечки из val.** Все статистики по train (приоры, профили, подкатегории) и дообучение моделей для val считаются только по train-fit.
4. **Корпус.**
   - *val v1* = корпус бенчмарка + позитивы val. Оказался оптимистичным: 0.870 против 0.809 на бенчмарке. Причина в том, что корпус бенчмарка похож на склейку выдач по его же запросам (~60–77 объявлений на запрос). У запроса бенчмарка много «конкурентов» — похожих объявлений из той же локации: медиана 9 против 2 у val ([experiments/03](experiments/03_competitors.py)).
   - *val v2*: для каждого val-запроса добавлено 100 похожих объявлений из train-fit из «его» локаций. Это случайная выборка из top-200 BM25, а не сам top, иначе дистракторы были бы подогнаны строго против BM25. Число 100 подобрано так, чтобы бейзлайн давал на val то же, что на бенчмарке: 0.817 против 0.809 ([experiments/04](experiments/04_hard_validation.py)).
5. **Ранкер.** Качество ранкера меряется 5-fold кросс-валидацией по запросам. Прирост меньше ~0.004 не отличить от шума, поэтому ключевые решения проверялись на трёх сидах с парной по запросам оценкой ошибки.

Разрыв «val v2 → бенчмарк» на пяти отправках: 0.008, 0.016, 0.017, 0.019, 0.020. Он стабилен, так что валидация предсказывала результат каждой отправки заранее.

## Анализ ошибок и что с ними сделано

Скрипты: [07](experiments/07_error_analysis.py), [08](experiments/08_learning_curve.py), [09](experiments/09_megacity.py).

**Куда терялись релевантные объявления** (sub3): 89.6% найдено, 6.5% были среди кандидатов, но ниже 50-го места, 3.9% не попали в кандидаты. У 87.5% из последних «чужая» локация.

| Сегмент | доля запросов | Recall@50, sub3 | доля всех потерь | Recall@50, sub5 |
|---|---|---|---|---|
| поиск по региону | 15% | 0.785 | 32% | 0.828 |
| мегаполисы (>10 тыс. объявлений в корпусе) | 17% | 0.813 | 31% | 0.840 |
| остальные города | 68% | ~0.94 | 37% | — |

1. **Поиск по региону.** У четверти релевантных объявлений приор ≤ 0.02: исполнитель из небольшого города внутри области. Что сделано: гео-признаки и отдельный источник кандидатов с малым весом локации. Каждое улучшение по отдельности дало +0.009 и +0.002, вместе +0.015: новые кандидаты полезны, только когда ранкеру есть чем их оценить.
2. **Мегаполисы.** В медиане ~200 кандидатов той же подкатегории. У 68% вытесненных позитивов ни один отдельный скор не ставил их в top-50: текстовые сигналы не различают почти одинаковые объявления.
   - *Помог* профиль кликов похожих запросов: +0.005 ± 0.002, вместе с косинусом e5-small +0.008 ± 0.002.
   - *Не помогли:*
     - расширение обучающей выборки ранкера: кривая обучения выходит на плато после ~1800 запросов;
     - cross-encoder вторым уровнем: 0.9135 против 0.9134, блендинг рангов даёт +0.002 в пределах шума. Вероятная причина: его сигнал уже покрыт дообученным bi-encoder'ом и профилем, а среди hard negatives остаются синонимичные «ложные негативы».

### Ловушки переноса val → бенчмарк
- **История кликов объявления.** В val-корпусе история есть у 49% объявлений (дистракторы взяты из train), в корпусе бенчмарка у 10%. Признак «объявление кликали раньше» выучил бы на val связь, которой на бенчмарке нет, поэтому он не используется. В профиле кликов вклад самого кандидата вычитается (leave-item-out).
- **Источник объявления.** По статичным признакам (отзывы, цена, длина текста) объявление из train отличается от объявления бенчмарка с AUC 0.58. Эти признаки исключены из ранкера, на val это стоит всего 0.002.
- **Согласованность моделей.** Ранкер учится на признаках `ft-val`, а применяется к признакам `ft-full`. Это версии одной модели, поэтому распределения косинусов совпадают. Веса фьюжна пришлось перенастроить при переходе с e5-small на дообученную модель: 0.891 → 0.898.

### Отвергнутые гипотезы
- «Промахи по локации — это удалённая работа». Нет: 7.2% против 6.6% уходов в другой город.
- «Невиденные запросы проваливаются». Нет: 0.897 против 0.900, дообученная модель хорошо обобщает.
- Параметры фильтров запроса в тексте для BM25: хуже, 0.426 против 0.430.
- Жёсткий фильтр по локации: хуже мягкого приора.

```
  bm25.py                  разреженный BM25

```

## Технические заметки
- `query_id` и `item_id` везде читаются и пишутся как строки. `check_answer.py` проверяет все требования ТЗ к файлу.
- **macOS:** `lightgbm` нужно импортировать раньше `torch`, иначе две копии OpenMP конфликтуют и обучение LightGBM падает с segfault. В `src/pipeline.py` порядок импортов учтён.
- **Память:** тексты хранятся как Arrow-строки (`string[pyarrow]`), кэш лемм читается потоково. Без этого 340 тыс. объявлений с описаниями занимали на 10+ ГБ больше.
